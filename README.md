Сможет ли она выполнить ls? Не сможет. Текст прямо указывает что r на каталоге это про список имён ls. Без права r команда ls не сможет прочитать содержимое каталога и выдаст ошибку доступа.
Объясняется это тем что r и x на каталогах отвечают за разные вещи. r позволяет только смотреть список имён,а x заходить внутрь и брать их.

3 Если бы  webapp  состоял в группе  sudo, то согласно правилу  %sudo ALL=(ALL:ALL) ALL, злоумышленник получил бы возможность выполнять абсолютно любые команды от имени root. Это означало бы полный захват системы.

Связка  nologin  + точечное правило ограничивает ущерб. nologin запрещает интерактивный вход. У злоумышленника не будет командной строки, что сильно усложняет ручное исследование системы и закрепление в ней.

Точечное правило sudo ( NOPASSWD: /usr/bin/systemctl restart webapp ) реализует принцип наименьших привилегий. Злоумышленник может использовать  sudo  только для перезапуска своего сервиса. Он не сможет через  sudo  прочитать  /etc/shadow, изменить системные файлы или установить бэкдор.
Итог вместо полного контроля над сервером (как в группе  sudo ), взломщик заперт в рамках одного конкретного действия, что спасает систему от полной компрометации.
4 Опасность  chmod 777  для владельца и остальных
Он не даёт дополнительные возможности самому  webapp. При правах  700 -rwx------ владелец  webapp  уже имеет полный доступ rwx к файлу. Права для остальных никак не расширяет возможности самого владельца.
Кому конкретно 777 открыл доступ? 777  означает, что читать, писать и исполнять могут вообще все, включая любого пользователя и любой процесс на машине. Опасность 777 скорее заключается именно во второй и третьей триаде. Если при  700  файл был изолирован и доступен только  webapp , то при  777  к конфигу получили доступ все остальные пользователи сервера: alice, bob или любой другой).
